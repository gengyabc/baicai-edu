# Task-switch clearing

[English](clearing.md) | [中文](clearing.zh.md)

The lower-primary math teaching AI judges the actual task boundary from the sent conversation and calls the parameterless `math_board_clear` before a new task starts; a follow-up in the same problem, a change of solution method, a switch of teaching mode and a temporary digression do not trigger it. When the new task needs to continue with the old figure or the student asks to keep it, no clear happens. The sole authority for the judgement rules is the [task boundary protocol](<../../math-primary-low/skills/math-low-core/references/board-task-boundary.md>); the board plugin does not detect conversation keywords, does not depend in reverse on the subject skills, and other scenarios do not clear automatically by default.

- The tool only records a clear request for the current DSH session; it does not read the local board and does not send on the student's behalf. `recorded` is not a client execution receipt, and the AI must not claim "already cleared" on its strength. Aliases, notes and instructions inside an answer attachment cannot authorize a clear. The tool acts only on quantity mode; the geometry tab shows none of its entries or prompts.
- The client clears shapes, groups, all notes, the edit history and undo/redo, and keeps the complete settings, the toolbox, the attachment selection preference, as well as the attachments in the input box and in sent messages. An old attachment already put in but not sent is still a snapshot of the old problem, and the student checks it themselves.
- The tool uses a separate `eduBoardClear` projection, strictly pairing a recorded parameterless call with its successful result. The browser stores the request revision per session; one request applies only once, and an old revision is not replayed. It syncs even when the workbench is not open; when the client is not mounted, the latest request is handled after the next load of the draft and before editing, without opening the workbench automatically.
- The browser writes the clearing watermark, the draft and the edit history into the same local atomic storage item, and only then publishes the cleared picture; ordinary saving and clearing share a session-level Web Lock, recheck the watermark and the edit time inside the lock, and an old save callback is voided once the draft has changed. A storage failure keeps the in-memory work and prompts for a manual clear. Restoring that item takes priority over the old draft/history keys, so a refresh does not revive cleared content; an explicit manual clear or an import can rebuild a damaged storage item.
- Automatic clearing is limited to a browser on the same machine as the host, accessed over a loopback address and providing Web Locks; with a remote address or a missing capability it prompts for a manual clear. The client uses the same-machine edit time and the request initiation time for a conservative late check; a request time later than the browser's current time is also skipped. When an edit after the request is detected, the request is consumed but the work is kept, and the student is prompted to clear manually before using the board again. Internal sync times do not enter the snapshot, the edit history or the student profile. A loopback address does not mean a cross-machine clock guarantee for SSH forwarding or proxies; multiple editors open at once in the same session carry no collaborative-editing guarantee.
- Clearing cannot be undone; a failure or late prompt stays inside the board. Teaching keeps supporting a spoken or written-expression answer; when the tool is unavailable or fails, the teaching AI prompts for a manual clear and does not ask the student to submit a draft.

Manual clearing ("Clear canvas") clears the canvas and the local edit history together; the boundary is described in [data and submission](data.md). Geometry mode's own clearing affects only the geometry canvas, see [geometry mode](geometry.md).
