# Learning Recommendation

## 1. Entry and Input

Enter when the student requests a recommendation, wants to learn but does not know what, wants different content, chooses `ui.stage.switch_content` in a stage choice, or the lifecycle's restricted **Math cold opening** condition applies. Ordinary entry into other subjects or general teaching does not auto-recommend; this skill does not independently broaden the lifecycle gate. When the student only chats, declines learning, or states real-world constraints without asking for learning suggestions, hand off to the support gate and do not turn it into a recommendation request. An explicit learning goal (including one raised during recommendation) goes straight to the lifecycle without listing recommendations first; if the student only wants to end today's learning, follow the end flow and do not use recommendations to retain them.

Load `learn-core` and `learn-data` (only the ones not yet loaded this session; reuse already loaded ones per `learn-core`'s "Load Once, Reuse After"), and reuse the current student, subject, snapshot, latest real performance, and original context provided by the lifecycle; if the snapshot is missing, read it per Read Snapshot in `learn-data`. With no current student or subject, handle it per the lifecycle gates and do not guess identity. If a `finalize_plan` exists, hand off to the lifecycle to recover the save first, and take over the recommendation request only after it succeeds. Within a subject, the recommendation scope is always the current subject; the general path offers cross-domain goal exploration only when the student asks to explore other areas, and never mixes capability evidence across subjects. Exploring and actually switching are separate.

Reuse teaching per `references/teaching-resolver.md` in `learn-data`, and read the "Learning recommendation" file in that core's subject contract (the resolved `teaching.core_skill`). It owns candidate content, difficulty, ordering, and the pedagogical rationale; this skill owns presentation and selection. When the package is missing or does not fit, use the general contract and keep helping. An existing old task lacking a recommendation role uses the general rules to give exploratory goals but keeps the current task's teaching and does not hot-swap it.

## 2. Form Candidates

Draw only from records already read and materials already sent: recent-session next steps, priority_targets, developing_topics, memory recommendations and difficulties, and milestones in the snapshot, plus the latest real performance. Do not scan raw, do not read unsent drafts or the board, and do not claim to know the full history.

- Following the subject's recommendation rules, form 2–3 distinct small goals that can start immediately and mark one as preferred; old candidates may be reordered by current performance and willingness to switch content. The fixed order of ordinary resume stays unchanged. The math cold opening uses the math contract's evidence ordering rather than auto-starting the first historical next_step; this does not replace unfinished-task restoration.
- Give each item a learning goal and how it will begin, chosen by the subject's recommendation role: resume unfinished reasoning, see an explained example then take over a step, investigate, or try an independent check. Store that opening description in `reason` alongside the evidence-based rationale so restored cards retain the same expectation; the preferred one also explains why it takes priority now. Reasons cite specific, verifiable performance and distinguish records, student self-report, and exploratory judgment; interests, grade, and difficulty preference are not mastery evidence. Pass already-clarified value connections, current support needs, and time/energy cost to the recommendation role, which decides the ordering; do not treat confidence or interest as mastery, and general records are only sourced references that cannot be mapped to specialist levels.
- The same candidate keeps its scope_id and teaching; a cross-domain candidate additionally includes the target subject/task description. Do not change session.json.subject before selection; for a cross-subject choice, the lifecycle first persists the authorization and handoff position per `references/teaching-transition.md` in `learn-data`, then saves the old subject, activates the identity with pending_transition, writes the target context, and clears state on both sides. Old cross-subject logs must not be moved into the new subject, and old materials must not be forced onto the new task.
- When records are insufficient, state clearly that this is an exploratory suggestion and give a low-barrier starting point using the known grade, interests, and subject defaults, without forcing a test first. If only one goal is suitable, give just one; do not recommend duplicate or unsuitable content to fill a quota.
- For `ui.recommend.want_switch`, give substantially different goals, not merely the current question with different numbers or names; valuable old suggestions may be kept but not pushed.

Return a temporary `recommendation` to the lifecycle: `subject`, `mode` (the mode of the existing context, otherwise the mode requested by this entry), `candidates` (each with `id`, `focus`, a `target_context` the subject's target classification can accept, a `reason` in the active UI locale, and an internal `basis`), and a single `preferred_id`. `basis` points to where the existing record is and the fact it supports, or notes that it is exploratory; store only the necessary summary. A math candidate may include the optional opening advice defined by `references/target-parsing.md` in `learn-data`; keep its focus a real topic and preserve student-authored intent. The advice is neither selection authorization nor evidence. Selecting “keep current” resumes the pending point rather than replacing the same goal's activity with an opening hint.

## 3. Present and Wait

Use `ask_user_question` to present short candidate labels as “learning goal · how we begin”, with their reasons, with the preferred one first and tagged with `ui.recommend.badge`; when needed, first state in one sentence why the preferred one takes priority. Mark an unfinished-task candidate as a continuation and name the missing step rather than presenting it as new learning. Keep full problem statements in the task context; the card uses a readable goal title. **Every candidate `reason` uses the active UI locale for all subjects**, and recommendation chrome (`ui.recommend.*` labels, badges, and prompts) may also use it, resolved per `references/ui-locale.md` in `learn-data`; content names may keep the subject's original language, and the teaching language after selection is still decided by the subject. Do not show internal fields, paths, or diagnostic jargon in the interface.

Deduplicate by the action and pending point, not wording. If a candidate already resumes the current task at its pending point, it serves as the keep-current route: omit the separate `ui.recommend.keep_current` option. Otherwise offer `ui.recommend.keep_current` when a current task exists; with no current task offer `ui.recommend.choose_own`. Always offer `ui.recommend.end_learning`, keeping the total number of options between 2 and 6. Custom input can still name the student's own goal. After presenting, wait: do not start teaching, generate a diagnostic question, finalize, or clear the board; focus, materials, mode, and the pending question stay unchanged.

## 4. Take Over the Choice

- A click, or typed input that means the same as a candidate: return the specific selected goal; an explicit delegation such as `ui.recommend.delegate_you_pick`, `ui.recommend.delegate_whatever`, or `ui.recommend.delegate_either` adopts the preferred candidate without further confirmation.
- `ui.recommend.keep_current`: clear the temporary recommendation and return to the original pending question or stage choice; with no original task, ask for one direction the student wants to learn.
- `ui.recommend.none_wanted`: do not repeat the same batch, clear the current candidates, and hand this wish to the lifecycle support gate without asking about a learning direction or turning activity chat into candidates; declining to learn does not mean ending. Only when the student still explicitly asks for other learning content, clarify one direction and update the candidates within this subject; crossing subjects still requires the original switch authorization.
- `ui.recommend.end_learning`: hand off to the lifecycle end flow.
- Skip (`ui.common.skip`), an empty message, and answers that cannot be mapped to an option are not selection authorization: keep the candidates and briefly state that the student can pick one, specify their own, or end, and do not auto-adopt the preferred one. This differs from the default advancement rule of the ordinary stage menu.

On session resume, use the same recommendation in the log: if still unselected, keep waiting and do not mistake a reply for an answer to the old question; if a valid selected_id exists, hand the authorized goal to the lifecycle and do not show the candidates again. A retry after a save failure keeps the selected goal and consumes it only once the new context is written successfully; saving alone does not auto-start teaching, and an explicit end or cancel takes priority. If the student identity or subject does not match, discard the old recommendation and reprocess from the current snapshot.

**Exit**: return only the pending candidates, the selected goal, retention of the original task, or an end intent. The presentation, selection, rejection, and preference answers of a recommendation are not learning performance: they produce no segment and do not rewrite existing `recommended_targets` or the long-term profile. After the student selects or explicitly delegates, the lifecycle performs the actual task switch under the original save gates; if it is still the original goal, resume it and do not fabricate a topic change. Board boundaries are determined only by the existing rules of the actual teaching task.

This skill's base directory holds every file it names: a `references/<name>.md` path below is the installed `<name>.md` beside that base directory, because an installed skill keeps no `references/` folder for prose. Locale catalogs do keep theirs, at `references/locales/<locale>.json`.
